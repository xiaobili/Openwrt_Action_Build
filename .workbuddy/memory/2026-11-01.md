## 排查 X86_64-Parallel-Combined-FULL 编译失败（IMMORTAL 作业）

**结论**：`package/feeds/passwall_packages/xray-core` 失败，根因是 Go 版本不匹配。
- 上游 Xray v26.10.31 的 go.mod 已改为 `go 1.27`
- ImmortalWrt `openwrt-25.12` 的 packages feed：`golang-values.mk` 里 `GO_DEFAULT_VERSION:=1.26`（golang1.26 = 1.26.10）
- xray-core Makefile 用 `PKG_BUILD_DEPENDS:=golang/host`（= 默认版本），`GOTOOLCHAIN=local` 禁止自动升级
- 报错：`go: ../../go.mod requires go >= 1.27 (running go 1.26.10; GOTOOLCHAIN=local)`

**修复方向**：把 xray-core 的 `PKG_BUILD_DEPENDS` 改成 `golang1.27/host`（feed 里已有 golang1.27=1.27.3，且本次构建中已 host-compile 成功）。
注意：必须在 `./scripts/feeds install -a` 之后（即 DIY 步骤 / 加载自定义配置）改，因为 build.yml 的「加载 Patch」步骤早于 feeds install，那时 `feeds/passwall_packages/xray-core/` 还不存在。

**机制要点（回答"为什么识别不到 1.27"）**
- `golang/` 是 dummy 包：`PKG_VERSION:=$(GO_DEFAULT_VERSION)`、`HOST_BUILD_DEPENDS:=golang$(PKG_VERSION)/host`。
- `golang-values.mk:128` `GO_HOST_VERSION:=$(patsubst golang%/host,%,$(filter golang%/host,$(PKG_BUILD_DEPENDS)))`，为空则回落 `GO_DEFAULT_VERSION`。
- `golang-package.mk:182` `PATH=$(STAGING_DIR_HOSTPKG)/lib/go-$(GO_HOST_VERSION)/bin:$(PATH)`；`golang-package.mk:224` `GOTOOLCHAIN=local`。
- 所以"用哪个 Go"完全由 Makefile 字符串决定，不读 go.mod；go.mod 的 `go 1.27` 只在编译阶段由 go 二进制校验。
- **注意**：只能整行替换，不能在 `PKG_BUILD_DEPENDS` 里追加 `golang1.27/host`——实测 `patsubst` 得到 `" 1.27"`（两个词带前导空格），PATH 会被拼坏。

**已验证的补丁片段（本地用真实 xray Makefile 跑过）**
- 上游 feed 目前仍是 `PKG_BUILD_DEPENDS:=golang/host`（确认非缓存问题），Immortal 默认 `GO_DEFAULT_VERSION:=1.26` 未变。
- sed 整行替换 + `grep -q 'golang/host'` 幂等判断有效：首次输出「切换 golang1.27/host」，第二次输出「已钉定，跳过」。

**其他发现**
- matrix 里 `fix_golang:"false"`，patch/fix_version_error.sh 根本没跑；且它的实现只 sed `golang/Makefile` 的 GO_VERSION_MAJOR_MINOR，对 ImmortalWrt 的多版本 golang（golang1.26/golang1.27 + GO_DEFAULT_VERSION）已失效。
- LEDE 侧 golang 已是 1.27.3，所以只有 IMMORTAL 挂。
- kconfig `recursive dependency detected: PACKAGE_luci-app-weechat` 是警告，非致命。
- retry-make.sh 对确定性编译错误重试 3 次是纯浪费。

## 变更：fix_golang_version 的 Go 版本来源改为「最新稳定版」

按用户要求，`lib/fix.sh: fix_golang_version()` 不再以 Xray-core `main` 分支 go.mod 为准，改为取 Go 官方最新稳定版。
- 新增 `_extract_go_version <body>`：兼容两种响应——`VERSION?m=text` 首行 `go1.27.3`，以及 `dl/?mode=json` 里的 `"version": "go1.27.3"`；只接受 `X.Y[.Z]` 纯数字稳定版（rc/beta 直接放弃）。
- 新增 `go_latest_stable_version()`：三级降级 `go.dev/VERSION?m=text` → `golang.org/VERSION?m=text`（换域名绕 DNS/CDN）→ `go.dev/dl/?mode=json`，全失败返回 1。
- `fix_golang_version` 调用上面的函数，其余逻辑（备份 .bak、sed 改 GO_VERSION_MAJOR_MINOR/PATCH、按 `dl.google.com/go/go$ver.src.tar.gz.sha256` 同步 PKG_HASH/MD5SUM/SHA256SUM）保持不变。
- 注意：`dl.google.com/go/VERSION?m=text` 是 404，别当镜像用（已实测）；`storage.googleapis.com/golang/VERSION` 也是 403。
- `go_xray_required_version()` / `pin_xray_go_version()` 未动，仍是独立的「按 xray go.mod 钉 golangX.Y/host」机制。

验证：真实网络拉到 1.27.3 并成功改写 Makefile + 写入官方 sha256（6e7749035c…）；mock 覆盖 6 条降级/异常分支全部符合预期；`bash -n` 与 `bash scripts/lint.sh` 均通过（shellcheck 未安装）。

## 排查 LEDE FULL 编译失败（X86_64-Parallel-LEDE，日志 19:39–19:59）

**结论**：不是内核/配置/源码问题，是**工具链缓存里的 `staging_dir/host` 残缺**，且命中缓存后本次构建跳过了 tools/toolchain 重建，导致残缺无法修复。

**证据链**
- 首次失败只花 26 s：`make[3] -C target/linux compile` 19:57:38 → `ERROR: target/linux failed to build` 19:58:04。
- 第 3 次重试后工作流兜底 `|| make -j$(nproc) V=s`（build.yml:224）打出真错：
  - `flex: fatal internal error, exec of .../staging_dir/host/bin/m4 failed`
  - `bison: .../staging_dir/host/share/bison/m4sugar/m4sugar.m4: cannot open: No such file or directory`
  - → `Makefile:754: olddefconfig` → `.modules` → `target/linux` 失败
- 整段 `make world` 只出现 `package/cleanup` / `target/compile`，**没有 `tools/compile`、`toolchain/compile`**；全日志唯一一次 tools 编译是 download 阶段的 `tools/flock/compile`（flock 是缓存之后上游新加的工具）。
- 缓存：`xiaobili/cachewrtbuild@main`，key `lede-master-x86-64-FULL-cache-openwrt-ff7be3fa2`，仅 401 MB，`Cache restored successfully`；`toolchain:true` → 缓存 staging_dir；`skip:true`（默认）→ 命中即跳过工具链编译。

**排除**：磁盘（失败时工作卷 106G/用 5.5G/剩 101G；根分区 99% 是 maximize-build-space 的 pv.img 占位，属预期）；下载（`下载源码包 成功完成`）；patch/diy 脚本（全仓库无任何脚本碰 staging_dir）。

**修复方向**
1. 删缓存或换 mixkey（换 cache action 不够：mixkey 相同则 key 前缀相同，坏缓存照样命中）。
2. build.yml 在「缓存工具链」之后加自检：`staging_dir/host/bin/{m4,bison,flex}` 可执行 + `share/bison/m4sugar/m4sugar.m4` 存在，否则清 tools 的 stamp 并 `make tools/compile V=s` 自愈。
3. 可选 `skip: false` 让每次校验/重建工具链。
4. 兜底风险：`retry-make.sh` 的 `mktemp` 落在 `/tmp`（在根分区），根分区只剩 ~1.8G。
